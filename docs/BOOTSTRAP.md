# Code Conductor Bootstrap Runbook

## Goal

Bring a clean workstation and a target repository to a validated Code Conductor-ready state without relying on hidden chat context.

## 1. Workstation baseline

Install and validate the current supported versions of:

- VS Code
- Git
- Node.js
- GitHub CLI
- Microsoft APM CLI
- Claude Code CLI
- OpenAI Codex CLI
- Kiro CLI
- Google Antigravity CLI
- Terraform CLI when Terraform work is expected
- Ansible tooling when Ansible work is expected
- Azure CLI, AWS CLI, and Google Cloud CLI only for projects that need those clouds

For Windows, prefer WSL2 or a Dev Container for agent execution where Linux sandbox/tool compatibility is materially better, while keeping VS Code as the primary UI.

## 2. Authenticate in order

Recommended order:

1. GitHub / VS Code / Copilot
2. Claude Code using Claude subscription authentication
3. Codex using ChatGPT subscription authentication
4. Kiro using official Kiro Pro authentication
5. Antigravity using official Google authentication
6. cloud CLIs/IAM only as required by the repository
7. Perplexity remains manual Pro-client research unless separately billed official MCP/API automation is explicitly enabled

Do not copy consumer OAuth/session tokens into repository configuration.

## 3. Clone Code Conductor

```bash
git clone https://github.com/saulpatinojr/Proj-Code_Conductor.git
cd Proj-Code_Conductor
```

`git clone` checks out `main`, which is the default branch and carries the current
baseline. No additional `git switch` step is required.

## 4. Read operating law before execution

Every human/agent should read in this order:

1. `AGENTS.md`
2. `docs/DECISIONS.md`
3. `STARTER.md`
4. `docs/IMPLEMENTATION-PLAN.md`
5. `docs/ARCHITECTURE.md`
6. relevant role/risk/capability configuration

`docs/DECISIONS.md` is the durable user-approved decision register. Do not silently reverse a locked decision.

## 5. Validate APM

Use the installed current/pinned APM CLI against the repository:

```bash
apm targets
apm install
apm audit --ci
```

Expected foundation targets:

- Copilot
- Claude
- Codex
- Kiro
- Antigravity
- Agent Skills

If the current APM release uses different exact target identifiers or manifest rules, do not guess. Capture the official evidence, update the manifest through an ADR, rerun the audit, and commit the generated lock/projections.

`apm.lock.yaml` must be generated by APM, never hand-authored.

## 6. Install project dependencies

Phase 1 will define the exact Node package manager/workspace tooling. Once committed, use the repository's pinned/package-manager declaration rather than a global assumption.

## 7. Run Code Conductor diagnostics

Once implemented:

```bash
ccon doctor
ccon validate
```

`ccon doctor` should verify:

- repository trust
- Git status
- APM state
- vendor client presence
- authentication/billing mode without exposing secrets
- conflicting AI API-key variables
- relevant MCP health
- sandbox capability
- GitHub connectivity

`ccon validate` should verify committed Code Conductor policy/configuration and reject invalid authority/risk combinations.

## 8. Target repository bootstrap

Future target repos use:

```bash
ccon init
```

The initializer should detect repository profile(s) and propose a minimal configuration, such as:

- application
- terraform
- terraform-azure
- terraform-aws
- terraform-gcp
- ansible
- azure-devops

The user approves before generated files are written.

Expected repository-level artifacts may include:

```text
AGENTS.md
apm.yml
apm.lock.yaml
apm-policy.yml
.conductor/
.github/
.vscode/
```

Only create files required by the selected profile/harness targets.

## 9. First dogfood run

The first complete orchestration run should occur against Code Conductor itself:

1. create a task from Phase 1 acceptance criteria;
2. classify R1/R2;
3. Kiro produces/validates the implementation spec when substantial enough;
4. Codex or Claude implements in an isolated worktree;
5. deterministic tests run;
6. a different provider acts as challenger/reviewer for R2;
7. validator reruns tests from a clean/integrated state;
8. GitHub PR is created/updated;
9. GitHub Copilot Gatekeeper reviews the PR;
10. structured evidence is collected;
11. human reviews before merge when policy requires.

## 10. Failure rule

Do not repair bootstrap failures by silently bypassing security, package integrity, authentication boundaries, or required checks.

Instead:

1. record the failing command/component;
2. capture non-secret diagnostics;
3. verify current official documentation;
4. document a required architecture change in an ADR if necessary;
5. update tests/configuration and rerun validation.
