## 0.1.2 (2026-10-21, beta pre-release)

Prepared 2026-10-21 from `main`; the tag decides the release date (`docs/RELEASE.md`). An odd minor version marks a pre-release.

### Added

- `docs/DOGFOOD-FIXTURE.md` documents the practice repository used for quick dogfood runs (now `Proj-Code_Conductor_Fixture`, formerly `cc-dogfood-fixture`): what it is and why it is separate, how to use it, what archiving it does to a run, and every file needed to rebuild it.

### Changed

- Code Conductor writes only under `~/.code-conductor` (or `$CODE_CONDUCTOR_HOME`). The short-lived working folders (`cc-pr-`, `cc-tree-`, `cc-smoke-`, `cc-probe-`) now live in its `tmp/` folder instead of the operating system's temporary folder, and the owner scripts write their reports to `reports/` and their `gh` request files to `tmp/` instead of the temporary folder. `CODE_CONDUCTOR_WORKSTATION_STATE` is removed: the smoke-test trust file is always `workstation.json` in the Code Conductor folder. `tests/core/home.test.ts` fails if shipped source goes back to the operating system's temporary folder.
- Packs are installed from `hybridcloudworks/Proj-AgentPacks`, the company-owned mirror of the Agent Packs source repository (main and release tags), not from the personal repository: `apm.yml` points there and the lock was re-materialized (same commits, same hashes; `apm audit` 31 of 31). `apm install hybridcloudworks/Proj-AgentPacks` installs the whole catalog, `-g` into the user profile for every client; verified in a scratch project: 39 agents and 236 skills in each of the Claude, Codex, Copilot and Kiro folders.

### Removed

- The `CODE_CONDUCTOR_WORKSTATION_STATE` setting. The smoke-test trust file is always `workstation.json` in the Code Conductor folder (`~/.code-conductor`, or `$CODE_CONDUCTOR_HOME`). If you had set the old variable, unset it and either copy that file to the new location or run `ccon harness-smoke` again for each client. If you never set it, nothing changes.

- `ccon import <run-manifest.json>` validates an external `RunManifest` (for example from Code Workflow's `export`) and stores it in the private run store as `import-<runId>`; manifests carrying a `mergeDecision` or a `ready` recommendation are rejected (ADR 0011).
- Optional `AgentResult.notVerified` contract field; agents are instructed to declare checks they did not or could not verify, and malformed values fail closed (ADR 0011).
- Native interfaces (C03, #45; D-060): `ccon next` and the VS Code Runs view show each run's next native step. Steps include reviewing the agent worktree in Source Control, re-running interactively to approve, validating a harness, completing an assignment manually, fixing gates or findings, or opening a draft pull request yourself. Commands are shown or copied, never run. `ccon handoff` prints the exact prompt for a manual run. `RunManifest.worktrees` records agent worktrees. `ccon doctor` and the Connections view show the official sign-in command and documentation link per client.
- Local discovery and selective context (I10, #42; ADR 0007): context files are read through one descriptor opened without following symlinks. The kernel's path for that descriptor must be exactly the checked path, so a directory swapped for a symlink mid-read is refused, and hard-linked files are refused (a hard link can make a file from outside the workspace appear inside it). Only Linux (including WSL) exposes a descriptor's path to Node, so `ccon compress <file>` and the MCP `read_compressed_file` tool refuse to read files on macOS and Windows, before touching the path. A path that does not exist and one outside the roots get the same error, and every failed or redirected open gets one other error, so no single answer reveals whether a file exists elsewhere on the machine. A caller that can also rename folders in the workspace can still estimate it statistically over about a hundred reads; ADR 0007 records that residual. Startup keeps restoring fingerprinted, non-secret discovery without starting providers, ACP, MCP or APM.
- VS Code distribution (I01, #33; D-066): the `.vsix` now ships only the two bundles, the defaults, the schema, the icon and the docs, named by a `files` allowlist in the extension manifest; it no longer carries `tsconfig.tsbuildinfo`, per-file build output or declarations, nor stray files left in `apps/vscode`. Release preflight unpacks the package outside the checkout and runs it against an unrelated folder. Commands the extension copies name its bundled runtime instead of a `ccon` that is not on `PATH`, and a command is not offered when a value would not reach the program exactly: PowerShell's stop-parsing token `--%` on any platform, and, for PowerShell, an empty argument, an embedded double quote or a spaced argument ending in a backslash. `docs/INSTALL.md` covers prerequisites, compatibility, install, update and uninstall.
- Client states (I02, #34; D-065): a provider starts only when its official client reports a sign-in (`claude auth status`, `codex login status`, `kiro-cli whoami`) and, for subscription assignments, a subscription sign-in. Workstation trust is bound to the smoke-tested client version; an unreadable version is never trusted. `ccon doctor` reports installed, signed in, healthy and trusted separately. Status probes run with no prompt or repository, and keep no personal fields or key fragments. Claude Code runs with `--setting-sources user`, so a repository's Claude Code settings (`env`, `apiKeyHelper`, hooks) and `.mcp.json` cannot switch a subscription run to another credential or endpoint. The probes and the launch run the same client file from an absolute PATH entry, and both read the same configuration: relative `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `HOME` and `USERPROFILE` values are made absolute, empty ones are removed (Claude Code reads an empty `CLAUDE_CONFIG_DIR` as the working directory), and relative `ANTHROPIC_CONFIG_DIR` and XDG base directories are removed. A provider whose explicit configuration directory lies inside the repository (decided by file identity, so symlinks and case or spelling variants count) is not started, and `ccon harness-smoke` refuses it too. Results are read only from the client's final message.
- GitHub integration (I03, #35; D-064): `ccon github-gate` summarizes a pull request's native state (checks, reviews, stale approvals, merge state) read-only and is green only when every signal is. `ccon pr` previews the draft pull request for a run's agent branch. With `--create` it refuses sensitive or credential-bearing history (content or names), a remote that does not push to exactly one URL in the pull request's repository, and a base not yet on the remote. It asks for an approval bound to the exact push URL and text, with agent-reported credentials redacted and agent text rendered inert, then pushes that exact commit and nothing else (no tags or submodules, HTTPS or SSH only) without force or hooks using your Git credentials, and opens a draft with `gh`. It never merges or approves. `ccon github-gate` no longer passes `UNSTABLE` merge state or an unreported draft state. Repositories nested in an agent worktree are control state: one appearing stops a run, `ccon worktrees` keeps the worktree, and no Code Conductor Git command enters it. `git` and `gh` are run from absolute PATH entries only.
- Handoff packets (I05, #37; D-063): dependent assignments get a versioned packet with recipient, 24-hour expiry, authorised context, committed changes, `notVerified`, risks, prior findings, unresolved readiness disagreements and provenance. The packet is rendered into the prompt as claims to verify, stored owner-private, and digest-verified on read. `ccon handoff --json` prints it and refuses expired or altered packets. `ccon runs [--older-than <days> [--apply]]` lists and prunes local run evidence, keeping runs whose worktrees still exist. Packets are built only after the Git-control check passed, carry only what earlier agents' dependencies produced (committed files, not read-only claims), redact credential-looking strings, and render as a closed, JSON-quoted block that earlier agents cannot break out of; the disclosure approval names the packet. Imported manifests cannot carry handoffs.
- Agent worktrees (I04, #36; D-062): `ccon worktrees` lists recorded agent worktrees, and `--remove-clean` removes only clean ones while keeping their branches. Clean means content-exact, on the worktree's own `cc/` branch and under the Code Conductor root. `--cleanup-worktrees` applies the same rule, no longer throws on a kept worktree or hides the run outcome, and never prunes other worktrees. Neither runs Git in the worktrees of a run that stopped for a Git configuration change; gate commands that change Git configuration now stop the run too. Commits refuse new credential-looking strings and unscanned content, reported by location and kind only. Agent-made history is scanned blob by blob with no commit-count limit. Provider clients no longer receive separately billed API credentials, provider-selection variables (Bedrock, Vertex, Foundry, base URL, profiles, federation) or Git's repository-local variables; `KIRO_API_KEY` draws on subscription credits and is kept. A relative `CODE_CONDUCTOR_HOME` is resolved to an absolute path. Tests run with hermetic Git configuration.
- Declarative gate profiles (I06, #38; D-061): gates declare prerequisites (tool on `PATH`, installed dependencies) and fail closed without executing when they are missing; Code Conductor never installs them. New `pnpm` and `yarn` profiles take precedence over `node` via their lockfiles. `terraform validate` requires an initialised directory, and an explicit, advisory `terraform-plan` profile is never auto-detected. `ccon run --gate-profiles` chooses profiles for a run. Gate commands run in an isolated process group, reaped on exit and interruption, with timeout and 4 MiB output bounds; leftovers are terminated and a descendant holding the pipes cannot hang the run. Tools resolve from absolute `PATH` entries only, and that exact file runs and is shown in the approval. Advisory gates alone never establish readiness, and a missing prerequisite always blocks. Terraform/OpenTofu gates are limited to fmt/validate/plan (without `-out`)/version, and shells and command wrappers are rejected. The `terraform-plan` approval discloses that planning runs provider plugins and configuration-defined programs with your credentials. Gate evidence `sha256` covers the full untruncated output.
- Pre-action approvals (C02, #44; ADR 0013): `ccon run --execute` asks in the terminal immediately before starting a provider, disclosing context to it, running gate commands and committing. Each approval is bound by SHA-256 digest to the recipient, revision, working-tree content, prompt digest, exact gate command plan or exact commit tree; missing, denied, expired and changed-context approvals are refused and the run becomes `human_required`. Non-interactive runs cannot approve; the terminal prompt requires a request-derived confirmation code, so pre-typed input cannot answer it. Every retry is approved separately. `RunManifest.approvals` records non-secret evidence; `ccon import` rejects manifests carrying approvals. Denied commits leave changes uncommitted in the agent worktree.
- Code Conductor's own Git operations (agent commits, worktree creation, status/diff) never run repository hooks or a configured `core.fsmonitor` and ignore replace refs. Approved commits are created from the approved tree object (`git commit-tree` plus a compare-and-swap `update-ref`) under Code Conductor's own identity. Provider runs that change Git configuration or history files stop the run before any further Git operation. Commits an agent makes itself are named, their whole history is checked for sensitive paths, and they make the run `human_required`. Provider clients that ignore `SIGTERM` after a timeout are killed.
- Packaged configuration defaults (C01, #43): the seven canonical `config/*.yaml` documents ship with the policy package and VS Code distribution under a SHA-256 manifest; planner, gates, MCP, CLI and native views read them, so an unrelated workspace needs no Code Conductor source, config directory or APM scaffold.
- Bounded, schema-validated user (`~/.code-conductor/config.json`) and workspace (`.code-conductor/config.json`) preference overlays that can only reorder/narrow eligible harnesses or disable them; they cannot change risk roles, authority, independence, commands, MCP trust or billing. Symlinked, dangling, oversized or malformed overrides fail closed.
- `ccon workspace-validate <folder>` reports packaged/overlay provenance for an arbitrary workspace; `ccon validate` remains the strict source-repository check.
- Standalone bundle smoke test that runs the distributed CLI with only its packaged defaults/schema in an empty unrelated directory.
- ADR 0011 (Accepted) locking the Code Workflow sibling boundary and shared result contract, and ADR 0012 (Proposed) for provider-local subagent evidence hooks.

- Next actions treat run records as untrusted: `ccon next`, `ccon handoff` and the VS Code views show each value on one line with control and format characters replaced. Commands are quoted for the shell you paste into (POSIX or PowerShell), and a command is left out when a value cannot be shown exactly. A refused commit points to native review of the kept changes. A run stopped for a Git configuration change offers only a configuration check. Worktree paths are resolved through symlinks before review, and `ccon import` rejects worktree records. The extension shows a command before copying it.

### Changed

- Claude Code reviews run with `--max-turns 40`, the same budget as a modifying assignment, instead of 20 (#4). In the 2026-10-19 R1 dogfood one of two reviews of this repository stopped at a tool call on the 20th turn, after 174 seconds, without reaching its final `CC_RESULT_JSON` line. The blocker for such a result now says so (`Claude Code reported error_max_turns after 20 turn(s), stopped at tool_use`).

- Reviewers and gate commands run in the builder's worktree after its own commits were checked, and could add commits there unnamed and unscanned. `ccon next` then suggested a plain `git push` of the branch. Before the merge decision, Code Conductor now checks that the worktree's history still ends where the builder's check left it. Commits added since are named, with the steps that ran there, scanned and path-checked. A HEAD moved off the branch, or a rewritten branch, makes the run `human_required`; a credential, a sensitive path or a deleted branch blocks it. `ccon next` now suggests `ccon pr`, which scans exactly what it pushes. (From the security review of #104.)
- The check of an agent's own commits now reads both HEAD and the agent's branch. An agent could commit on its branch and then move HEAD back to the base (`git checkout --detach`): the worktree looked untouched, and the branch a person merges carried commits that were neither named nor scanned for credentials. Both are now checked. A HEAD that is not the branch tip makes the run `human_required`, and a branch the agent deleted blocks it.
  - After independent security review:
    - Every end of the history that names a commit is named and scanned before anything is refused, so a credential committed on a detached HEAD whose branch was then deleted is still reported.
    - Messages name where commits are: the branch, or HEAD with the branch it is on or `detached`.
    - The branch is looked up by its exact ref, so a tag spelt `refs/heads/<branch>` cannot stand in for it; `ccon pr` uses the same lookup.
    - Code Conductor's Git ignores commit-graph files: Git trusts the parents they record, so a rewritten one could hide commits from the history check.
    - Credential-shaped file names are redacted in every credential-scan finding: the history check, the commit approval and `ccon pr`.
    - Code Conductor's own commit is bound to the HEAD whose history was checked, with or without an approval, so a commit made after the check is never committed on top of.
- Found by the first live workstation validation, on Windows 11 (#4):
  - `ccon doctor` listed every VS Code extension as missing on Windows. `code` is a batch file there (`code.cmd`), which Node cannot start without a shell, and Code Conductor does not run batch files through `cmd.exe`. Doctor now reads VS Code's own `extensions.json` (in `~/.vscode/extensions`, or `~/.vscode-server/extensions` on a remote host), which starts no process at all.
  - The `harness-smoke --mode modify` check accepts `WRITE_OK` with a CRLF line ending, as a client on Windows may write it, and now also requires `OUTPUT.txt` to be the only change. A failure names the value of each check: the result status with its reason, the changed files, and the start of `OUTPUT.txt`. Before, it gave only the exit code.
  - After independent review of that fix:
    - The smoke test now finds what a client changed by hashing every file in the workspace before and after, instead of trusting `git status`. Under `status.showUntrackedFiles=no` or a global exclude, `git status` printed nothing. Read mode then passed even when a client wrote files, and modify could never pass.
    - `OUTPUT.txt` may also carry a UTF-8 byte-order mark or be UTF-16LE, as PowerShell 5.1 writes them. It is read bounded, and never through a symlink.
    - The modify prompt now says to create or change no other file.
    - Doctor also reads `VSCODE_EXTENSIONS`, `VSCODE_PORTABLE` and Codespaces' `~/.vscode-remote`. It treats an empty `extensions.json` as no extensions, as VS Code does, and warns, naming the file, when one exists but cannot be read.
  - After independent review of that follow-up, which was merged before the review finished:
    - The smoke test's scan opens only regular files, bounded and never through a symlink. A FIFO a client left in the workspace made it block in `open()`, beyond the reach of Ctrl-C. It also records directories, special files and each file's executable bits. Read mode passed when a client made a tracked file executable, which `git status` had reported; it now fails, as it does when a client creates an empty folder.
    - A UTF-16LE `OUTPUT.txt` with a stray odd byte no longer passes.
    - Doctor also reads the VS Code server's `VSCODE_AGENT_FOLDER`, and shortens only paths inside the home folder to `~`.
  - Every `ccon run --execute` that created an agent worktree on Windows stopped before starting the provider, reporting that Git configuration had changed when nothing had.
    - **Cause:** the check compared the repository's shared configuration as read from the agent worktree with the reading from the primary checkout. On Windows, Git names `.git/config` with forward slashes in the agent worktree. Code Conductor turned the primary checkout's relative `.git/config` into a path with backslashes, so the two readings never matched. On any system, `includeIf "gitdir:..."` and `"onbranch:..."` also legitimately differ between the two.
    - **Fix:** each directory is now compared only with its own first reading. The directory that first read the repository is read again whenever another of its worktrees is checked, so a change an earlier assignment made there is still caught.
    - **Message:** a stop now names each configuration file, control file or nested repository that changed, appeared or disappeared, never a value.
    - After independent review: an agent worktree that stops being a Git work tree (its `.git` file removed, or `core.worktree` moved) now stops the run instead of skipping the check. A `.git` file pointed at another worktree's Git directory is a change. A repository the person creates in the primary checkout during a run no longer stops it. Code Conductor creates agent worktrees with absolute links, so `worktree.useRelativePaths=true` no longer makes Git enable `extensions.relativeWorktrees` in the repository, which also stopped the run.

- `ccon validate` checks `config/gates.yaml` against a `GateCatalog` JSON Schema (in `packages/schemas`), reporting each problem as `gates.catalog` at its exact key. A misspelt key such as `timeout` for `timeout_ms` is reported instead of ignored, wrong types in `detect`, `requires`, `blocking` or `timeout_ms` are caught before the catalog ships instead of making detection or prerequisite checks throw at run time, an empty `detect` file list (which matched every repository) is refused, timeouts must fit Node's timer (above 2147483647 ms, or `.inf`, a gate timed out after 1 ms), and profile and gate names must be plain. A `detect` with only `package_name`, and a profile that replaces itself, are reported too, since neither is ever selected. Keys that are not plain are shown quoted, so a line break in a key cannot forge an output line. An invalid `selection` is now `gates.catalog` rather than `gates.selection`.

### Fixed

- The result contract in every prompt now says what a finding is: a defect in the change, with evidence, blocking only when it must be fixed before merge; a check the agent could not run is not a finding and belongs in `notVerified`. The builder's rule says the same. In the 2026-10-20 run `CC-20261020033854-51b215cd` (#4) the builder completed, the reviewer recommended `ready` with 489 tests green, and all three deterministic gates passed, but the builder had filed its own sandbox limitation ("broader validation requires revalidation outside the current sandbox") as a blocking finding, so the merge decision was `blocked`. The decision rule is unchanged: an unresolved blocking finding still blocks, from any role.
- The builder's role rule now says what to do when the repository's validation tools are not installed in its worktree: do not install them, do not block, complete the change with `recommendation: review` and name each check it could not run in `notVerified`; the deterministic gates decide (D-054). In the 2026-10-20 run `CC-20261020032623-c12cf4c4` Codex read D-061 correctly, refused to install, and reported `blocked`, so the reviewer and the gates never ran. The dogfood runbook now says to install the dependencies in the worktree at the first approval prompt, before the builder starts.
- The assignment prompt now spells out the result contract (every allowed `status`, `recommendation`, `severity`, `kind` and gate status, the shapes of `tests`, `evidence` and `findings`, and one valid example), and a retry after a rejected result line tells the client why it was rejected. In the 2026-10-20 R1 dogfood (#4) the reviewer did a full review, found the suite green, and was rejected twice for reporting `"success"`, `"approve"` and `"suggestion"`, because the prompt named the fields but not their values and the retry repeated the same prompt. The retry's disclosure approval binds the new prompt.
- `ccon run --approval-ttl <minutes>`: how long each approval prompt waits for the person (default 15, at most 1440). The same dogfood's gate approval expired after 35 minutes and nothing was validated. Documented in `APPROVALS.md` and the dogfood runbook, with the note that an attended run should pass `--approval-ttl 60` and start from `main`.
- `scripts/package-vscode.mjs` runs the locked `@vscode/vsce` as a script under the current Node instead of through `npx.cmd`, which Node refuses to spawn without a shell on Windows (the script failed there with "exit code null"); CI on Linux was unaffected. Packaging now works on the owner's workstation.
- Gate evidence is bound to the commit `ccon pr` pushes (#111, F4 of the first R1 review). Read-only assignments run in the builder's worktree after its commit; before the gate commands run, the worktree's content is now compared with its HEAD commit, content-exact as the commit path does. A difference names the paths and the steps that ran there, runs no gate and makes the run `human_required`. Before, an edit a read-only agent left behind was inside what the gate approval bound and what the gates tested, while the pushed branch did not carry it. Regression: a reviewer that writes a file in the builder worktree.
- The unit suite runs natively on Windows (#4). The first native run on the owner's workstation had 83 failures, every one a test fixture's assumption: Git-heavy tests get 60 s there instead of 5 s (Linux keeps 5 s); fixtures no longer split paths on `/`, assert POSIX paths, extension-less executables, non-UTF-8 file names or the pre-D-074 `npm` command; and the owner-script tests, whose fake `gh` is a shell script the scripts cannot run on Windows (a `.cmd` shim breaks on `&` in API URLs under cmd.exe), are skipped there and run on Linux CI as before. No product code changed for this.
- The merge decision reported `ready` on four paths the 2026-10-19 R1 dogfood review found (#4; D-075): a completed reviewer recommending `changes_required` without a blocking finding, a `cancelled` assignment, a run with no results, and a run in which no deterministic gate ran (R0 planned no validator, so the fail-closed no-applicable-gates path was never reached and the rationale claimed gates had passed). Each now fails closed, `ready` requires a passed blocking gate, and R0 includes the internal validator as AGENTS.md section 5 requires. `mergeDecision` is exported for unit tests.
- A `CC_RESULT_JSON` completion claim overrode the client's exit status: a client that printed its report and then exited with an error or was ended by a signal counted as completed (#4; D-075). The runtime now trusts a completion claim only from a process that ended cleanly (the same rule `harness-smoke` applies), and a result without a structured report names how the client ended, with the client's own reason when its output states one: `Claude Code reported error_max_turns after 20 turn(s)`, `Codex reported turn.failed: ...`.
- `npm` and `npx` gates could not run on native Windows: the Node profile's `typecheck` and `unit-tests` gates reported `npm` as an unsupported batch shim, so every Node run on a Windows workstation ended `changes_required` (#4; D-074). They now run as the `node.exe` on `PATH` executing the `npm-cli.js` bundled in that Node installation; both files are in the approval summary and the approval digest, and the shim is never run. `pnpm` and `yarn` stay unsupported there.
- Codex never started (#4; D-073): the adapter passed `--ask-for-approval never` to `codex exec`, a flag the headless surface does not accept (its approval policy is already Never), so the client exited 2 with a usage error before any prompt ran. The flag is removed; the sandbox flag, `--cd` and `--json` stay. A failed `ccon harness-smoke` now prints the client's last stderr lines on its `SMOKE FAIL` line, redacted and escaped, so a usage error, a sandbox refusal or a cancelled permission is visible in the evidence.

### Security

- Local CodeQL (`security-and-quality`, 2026-10-19) findings fixed: a remote URL's query/fragment is now cut by index rather than a regular expression CodeQL rated polynomial; the Agent Catalog inventory script, the provider-native inventory and `ccon import` read each file through the one descriptor they check (no final symlink followed, size checked on the open file), instead of checking a path and then reading it by name; two unused imports removed. Actions queries reported nothing.

- Handoff disclosure summaries count redaction markers with an exact string search instead of a regular expression whose worst case is quadratic (CodeQL `js/polynomial-redos`). The serialized packet always puts a closing bracket after agent-written text, so the old count was already linear in practice; the count no longer depends on that layout.
- Subscription-first billing policy and detection of API-key environment variables that could bypass intended billing paths.
- Fail-closed structured agent-result parsing and explicit workstation trust before unattended CLI execution.
- Structured `AgentResult` payloads are validated against the canonical JSON Schema before runtime acceptance.
- Human approval boundary for high-risk/destructive external operations.
- Local run/evidence, workstation-trust, modifying worktree, and context-optimizer telemetry directories/files use owner-only permissions on POSIX systems where applicable.
- Context file reads are bounded to configured workspace roots after canonical/symlink resolution and reject sensitive/state paths, non-regular files, and oversized inputs.
- Agent and skill front matter, remote URLs, Git branch-name inputs and agent-catalog files are parsed in linear time. A long run of spaces in the front matter of an agent or skill file (`.claude/agents`, `.github/agents`, `SKILL.md` and the rest, in the open repository or your home folder) made `ccon agents` and `ccon doctor`, also run by the VS Code Doctor command, stall: about 27 s at 3 KB, and without practical bound near the 256 KB read limit, because the name pattern was cubic. Quadratic patterns are gone too, from remote URL redaction, GitHub repository detection, Git branch-name sanitization and the agent-catalog intake script's line trim and title. Results are unchanged, except for two cases. A name is now read only from its own top-level `name:` line: an empty `name:`, or a value on the next line, gives the file name, where it used to take the next line (`description: d`) as the name. A remote URL that cannot be parsed and spans lines is now shown as `[redacted]`: a line break could hide a query, or a credential before a later `@`, from the redaction.
- Evidence-store path traversal and rename-based sensitive-file detection are covered by regression tests.
- Added high/critical dependency audit as a CI gate; the current dependency graph reports zero known npm vulnerabilities.
- Multiple GitHub Copilot Gatekeeper review rounds were exercised and concrete findings were addressed with targeted regression coverage.
- The runtime test suite no longer commits a contributor's uncommitted work. Its worktree double returned the checkout running the suite as the builder's worktree, so `npm test` with uncommitted changes committed them onto the current branch under the Code Conductor identity, bounded only by the sensitive-path denylist. The tests now use real linked worktrees of a throwaway repository. As defense in depth, `commitAgentChanges` refuses any checkout other than the agent's own worktree. The worktree must pass all of these checks:
  - It is the top level of a linked worktree, not a primary working tree.
  - It has the handle's `cc/` agent branch checked out.
  - Git can report the worktree layout. The check fails closed when it cannot, as with Git older than 2.31.

  Git subprocesses, and the test suite, also drop Git's repository-local environment variables (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` and the rest of `git rev-parse --local-env-vars`). Otherwise, a run launched from a git hook or a dotfiles shell could be redirected onto a person's own checkout or index. Fixes #48.
- Gate shapes: a `node` gate script under a folder whose name ends in a dot is refused, because Windows drops the dot and `node_modules.` can name `node_modules` there. A malformed gate catalog is reported by `ccon validate` as `gates.catalog` instead of crashing it or passing. That covers an empty file, `profiles` or a profile that is not a mapping, a profile without a `gates` list (such as one written as its gates list, which also hid its commands from the gate checks), and a gate that is not a mapping.
